# Libiao(立镖) 3D 소터 — 조사 요약과 모델링 가정

## 실제 시스템 (공개 자료)

| 항목 | 내용 | 출처 |

| 회사 | Libiao Robotics(立镖机器人), 2016년 항저우 설립 | [TLI][tli], [Robot Report][rbr] |

| 투입 | 투입 스테이션은 그리드 둘레에 있음. 작업자가 소포를 로봇에 올림 | [TLI][tli] |

| 투하 방식 | 틸트 트레이 로봇(5 kg)과 크로스벨트 로봇(30 kg, 유럽용) 두 종류 | [TLI][tli] |

| 처리량 | 단층 모듈 시간당 3,000건 | [Robot Report][rbr] |

| 면적당 | JD 마충 200대/1,084 m²/9,000 h⁻¹, STO 톈진 약 500대/2,350 m²/22,000 h⁻¹, 중국우정 항저우 약 700대/3,200 m²/30,000 h⁻¹ → 약 8~9.4건/m²/h | [TLI][tli] |
| 다층 | 롯데글로벌로지스(서울, 2023) "twin level tSort" 2층 시스템 | [Forkliftaction][fa] |
| 장점 | 컨베이어식 대비 면적 1/5~1/3, 확장·이전이 쉬움, 오류율 0.01% 이하(주장) | [TLI][tli], [36kr][36kr], [Forkliftaction][fa] |

**공개 자료에 없는 것**: 로봇 치수·속도, 플랫폼 높이, 셀 피치, 자루 크기. 아래 값은 사진과 일반적인 소형 분류 AGV 수치로 잡은 **가정**입니다.

## 이 모델의 가정

| 항목 | 값 | 비고 |
|---|---|---|
| 데크 | 19 × 13 셀, 셀 0.70 m (13.3 × 9.1 m) + 앞뒤 스테이션 행 | |
| 데크 높이 | 2.40 m | 아래층에서 자루 교체 작업 가능한 높이로 가정 |
| 통로/슈트 | 3셀마다 통로 행·열, 나머지는 2×2 슈트 블록 → 슈트 96개, 통로 셀 163개 | 모든 슈트가 통로와 맞닿음 |
| 교통 규칙 | 일방통행 격자 (외곽 반시계 순환, 안쪽 행·열은 번갈아), 셀 예약으로 충돌 회피, 5초 막히면 우회 경로 | |

## 시뮬레이션 결과 (1시간, 1/60 s 스텝)

| 로봇 수 | 처리량 (건/h) | 로봇당 (건/h) | 앞이 막혀 기다린 시간 비율 |
|---|---|---|---|
| 10 | 1,170 | 117 | 3% |
| 20 | 2,080 | 104 | 6% |
| **30 (기본)** | **2,610** | **87** | **13%** |
| 40 | 2,830 | 71 | 22% |

- 기본 30대에서 데크 약 140 m²당 시간당 2,600건 → **약 19건/m²/h**. 실제 사례(8~9.4건/m²/h)는 사람 통로·충전·자루 교체 공간을 포함한 전체 면적 기준이라 수치가 더 낮습니다. 로봇 1대가 약 41초마다 1건을 처리하는 셈으로, 350대 15,000~20,000건/h 사례(로봇당 43~57건/h)보다 빠른 편입니다. 데크가 작아 평균 이동 거리가 짧기 때문입니다.
- 30대를 넘으면 투입 스테이션 6개와 통로 혼잡이 병목이 되어 로봇당 처리량이 떨어집니다. 단층 모듈 3,000건/h(Robot Report)와 비슷한 상한입니다.

## 같은 로직의 세 가지 구현

- `web/libiao-sim-core.js` — 기준 구현 (Node/브라우저)
- `tools/export_libiao_trace.js` — 600초 워밍업 후 30초를 30fps로 기록 → `blender/libiao_trace.json`
- `Assets/Libiao/Scripts/LibiaoSim.cs` — Unity C# 포팅. 같은 mulberry32 난수 사용. 1시간 실행 결과가 JS와 1% 이내로 일치 (설정값 float 반올림 차이)
