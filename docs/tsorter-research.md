# Libiao T-Sort (핑거형 플랫폼 소터) — 조사 요약과 모델링 가정

"리비아오 T-Sorter"는 Libiao Robotics(立镖机器人)의 **T-Sort 분류 솔루션**으로 보고 만들었습니다. 공식 사이트에 "T-Sorter"라는 이름의 제품은 없고, 솔루션 메뉴에 *T-Sort Sorting Solutions* 와 *3D Sorting Solutions* 두 가지가 있습니다.

이 저장소의 기존 Libiao 장면(`docs/libiao-research.md`)은 구멍 뚫린 강판 격자 위를 로봇이 다니며 아래층 자루로 떨어뜨리는 **격자형 데크**입니다. 이번 장면은 공식 T-Sort 솔루션 그림에 나오는 **핑거형 플랫폼(Finger-type Platform)** 입니다. 넓은 메인 데크에서 빗살처럼 긴 핑거(데크 띠)가 뻗어 나가고, 로봇이 핑거 위를 달리다 옆 틈으로 소포를 떨어뜨리면 핑거 사이 바닥의 슈트 통에 모입니다.

## 이 모델의 가정

| 항목 | 값 | 비고 |
|---|---|---|
| 셀 | 0.60 m (로봇 480 mm + 여유) | 가정 |
| 데크 높이 | 1.10 m (작업자가 바닥에 서서 투입대에 올림) | 공식 그림의 비율로 가정 |
| 메인 데크 | 5 × 24 셀 (3.0 × 14.4 m) + 충전 줄 | |
| 핑거 | 6개 × 14 셀 (8.4 m), 폭 2셀(1.2 m) = 나가는 차선 + 돌아오는 차선, 끝에서 U턴 | 2차선은 교착 없는 일방통행을 위한 가정 |
| 슈트 | 핑거 차선 셀마다 바깥 틈 쪽에 1개 → 6 × 14 × 2 = **168개**. 틈 폭 1.2 m에 통 두 줄, 셀 경계마다 스테인리스 칸막이 | |
| 슈트 통 | 베이지 PP 0.50 × 0.50 m, 입구 높이 0.74 m, 용량 20개(가득 차면 교체) | 공식 그림의 베이지 슈트 |
| 투입 스테이션 | 메인 데크 왼쪽 4곳. U자 분기(대기 1칸 + 적재 1칸), 적재 2.0 s, 다음 소포 공급 1.2 s | |
| 로봇 | 30대, 0.48 × 0.38 × 0.23 m, 노란 차체, 좌우로 기울어지는 트레이(최대 35°) | 치수는 공식, 나머지 가정 |
| 주행 | 3.0 m/s, 1.5 m/s², 제자리 회전 180°/s | 가정 |
| 투하 | 트레이 기울임-복귀 0.9 s, 0.3 s 지점에서 소포가 틈으로 떨어짐 | 가정 |
| 교통 규칙 | 메인 데크 행은 번갈아 일방통행, 0·2열은 위로, 마지막 열은 아래로. 셀 예약으로 충돌 회피, 5 s 막히면 우회 | |
| 충전 | 충전 파일은 장면에만 있고, 시뮬레이션에서는 충전하지 않음 | 단순화 |

## 시뮬레이션 결과 (1시간, 1/60 s 스텝, seed 1~3 평균)

| 로봇 수 | 처리량 (건/h) | 로봇당 (건/h) | 앞이 막혀 기다린 시간 | 통 교체 |
|---|---|---|---|---|
| 10 | 1,046 | 105 | 3% | 13 |
| 20 | 1,777 | 89 | 8% | 57 |
| **30 (기본)** | **2,146** | **72** | **18%** | **79** |
| 40 | 2,069 | 52 | 35% | 75 |

- 기본 30대에서 시간당 약 2,100건으로, 공개 프로필의 "2000 Parts per hour" 와 비슷한 규모입니다.
- 30대를 넘으면 처리량이 늘지 않고 막혀 기다리는 시간만 늘어납니다. 투입 스테이션 4곳으로 가는 차량이 모두 메인 데크 왼쪽 열을 지나기 때문에, 그 열과 핑거 입구가 병목입니다. 처리량을 더 올리려면 투입 스테이션을 늘리거나 메인 데크 반대쪽에도 두는 편이 낫습니다(공식 설명대로 로봇·슈트·스테이션 수를 조정하는 방식).
- 2차선 핑거는 나가는 차선에서 아래쪽 슈트, U턴 후 돌아오는 차선에서 위쪽 슈트로 떨어뜨리므로 로봇끼리 마주치지 않습니다.

## 같은 로직의 세 가지 구현

- `web/tsorter-sim-core.js` — 기준 구현 (Node/브라우저)
- `tools/export_tsorter_trace.js` — 600초 워밍업 후 30초를 30fps로 기록 (1/60 s 스텝) → `blender/tsorter_trace.json`
- `Assets/TSorter/Scripts/TSorterSim.cs` — Unity C# 포팅. 같은 mulberry32 난수, 설정값 double. 로봇 12·30·48대, seed 1·3에서 1시간 처리 건수·막힌 시간·로봇 위치가 JS와 소수점 6자리까지 같음 (mono로 확인)

## 30초 영상 동선 (seed 3, warmup 600 s)

| 시간 | 장면 | 캡션 |
|---|---|---|
| 0~3 s | 앞 왼쪽 위에서 전체 (메인 데크 + 빗살 핑거 6개) | 타이틀 "T-Sort 핑거형 로봇 소터" |
| 3~8 s | 투입 스테이션으로 내려가 작업자 쪽에서 적재 | 01 투입 스테이션 |
| 8~12 s | 로봇 29가 핑거 2로 들어가고 카메라가 틈 위에서 나란히 달림 | 02 핑거 주행 → 틸트 투하 |
| 12.9 s | 핑거 끝에서 트레이를 기울여 투하, 통으로 떨어짐 | |
| 15~19 s | 핑거 끝을 돌아 핑거 2·3 사이 틈으로 파고들어 17.1 s 투하를 봄 | 03 슈트 통으로 분류 |
| 19~24 s | 위로 솟아올라 여러 핑거를 내려다봄 (21.8 s 투하) | 04 동시 다목적지 분류 |
| 24~30 s | 뒤쪽으로 돌아 27.0 s 투하 후 전경으로 빠짐 | 엔드 카드 (로봇·슈트·처리량) |

캡션은 Unity에서 별도 카메라가 투명 배경에 그려 녹화 프레임에 합성합니다. 메인 카메라의 피사계 심도·모션 블러가 글자에 걸리지 않습니다. 글꼴은 Windows의 맑은 고딕을 씁니다.

z-파이팅(깜빡임) 방지: 데크 판끼리 같은 면에서 겹치지 않게 경계를 1 mm 띄우고, QR·차선 표시는 1.5 mm 이상 띄우며, 핑거 가장자리 노란 띠는 윗면이 아닌 옆면에 붙였습니다. Unity 카메라 근접 클립은 0.05 m 입니다.
